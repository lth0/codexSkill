# 论文写作指南 / Thesis Writing Guide

本指南为论文写作模式（Step W0-W5）的详细执行指令。

---

## Step W0：环境准备（Environment Setup）

### W0.1 检查并创建 About/ 目录

**重要：About/ 目录必须创建在用户当前工作目录下（即 `pwd` 输出的目录），不是 Skill 安装目录，也不是用户的上级目录。**

执行流程：

```bash
# 第一步：确认当前工作目录
pwd
```

```bash
# 第二步：检查 About/ 是否存在
ls -d About/ 2>/dev/null
```

**情况 A：About/ 不存在**
- 执行 `mkdir -p About` 创建目录
- 向用户输出引导信息：

```
已创建 About/ 目录（路径：<pwd>/About/）

请将材料放入该目录，并注意按以下规则命名和放置：

1. **论文模板** (.docx)
   → About/论文模板.docx
   放入学校提供的毕业论文格式模板

2. **范文** (.docx / .pdf / .txt)
   → About/范文.docx
   同校同专业已通过的优秀论文（用于参考写作风格和章节深度）

3. **项目源代码** (.py / .java / .js / .cpp 等)
   → About/src/  （整个源代码目录复制或移动到此处）
   放入毕业设计/论文相关的完整源代码项目
   如果代码较多，只需放入核心业务代码（排除 node_modules、venv、build 等依赖目录）

4. **项目文档** (.md / .pdf / .txt)
   → About/项目文档.md（可多个）
   放入 README、API 文档、架构说明等

5. **其他材料**
   → About/ 下直接放置并备注用途
   如开题报告.docx、任务书.docx、格式规范.pdf 等

⚠️ 注意：代码必须放在 About/src/ 目录下，不要直接散落在 About/ 根目录，
否则可能被误识别为文档。

材料越多，生成的论文质量越高、格式越准确。
准备完成后告诉我"已准备好"。
```

**停止后续步骤，等待用户确认已放入文件。**

**情况 B：About/ 存在但为空**
- 向用户输出引导信息（同上），提示目录已存在但为空
- **停止后续步骤，等待用户确认已放入文件。**

**情况 C：About/ 存在且有文件**
- 直接进入 W0.2 扫描文件

### W0.2 扫描并分类文件

扫描 `About/` 目录，识别文件类型：

```bash
find About/ -type f | head -50
```

按类型分类：
- **模板文件**：文件名含 "模板""template""格式" 的 .docx
- **范文文件**：其他 .docx/.pdf/.txt 文件
- **代码文件**：.py/.java/.js/.ts/.cpp/.c/.go/.rs/.vue/.html 等
- **文档文件**：.md/.rst 等
- **其他**：图片、数据等

输出扫描结果摘要，告知用户检测到了哪些材料。

### W0.3 解析模板格式

对检测到的模板 .docx 文件执行格式分析：

```bash
python3 ~/.claude/skills/aigc-detector/scripts/docx_io.py analyze "About/<模板文件名>"
```

如果全局路径失败，回退到项目级路径：
```bash
python3 .claude/skills/aigc-detector/scripts/docx_io.py analyze "About/<模板文件名>"
```

将输出的格式元数据保存到上下文中，供 Step W4 使用。记录以下关键信息：
- 纸张大小和页边距
- 各级标题的字号、字体、加粗、对齐方式
- 正文的字号、字体、行距、首行缩进
- 章节编号格式（从 DOCUMENT STRUCTURE 部分识别）

## Step W1：材料分析（Material Analysis）

### W1.1 模板格式解析

基于 W0.3 的 `analyze` 输出，提取并记录以下格式规则：

**页面布局：**
- 纸张大小（A4 / Letter / 自定义）
- 页边距（上下左右，单位 cm）
- 装订线位置和宽度

**字体规则（从 FONT PATTERNS 中按字号排序提取）：**
- 最大字号 + 居中对齐 = 论文标题格式
- 次大字号 + 加粗 = 一级标题格式
- 第三大字号 + 加粗 = 二级标题格式
- 最常见小字号 = 正文字体

**段落格式（从 PARAGRAPH FORMATS 中提取）：**
- 行距（line_spacing）
- 首行缩进（first_line_indent）
- 段前段后间距

**文档结构（从 DOCUMENT STRUCTURE 中提取）：**
- 章节编号格式（"1 xxx" vs "第一章 xxx" vs "Chapter 1"）

### W1.2 范文分析

如果用户提供了范文，使用 `docx_io.py read` 读取：

```bash
python3 ~/.claude/skills/aigc-detector/scripts/docx_io.py read "About/<范文文件名>"
```

分析范文的以下方面：
- **章节结构**：采用了哪些章节，章节之间的逻辑关系
- **写作深度**：每章大约多少字，论证到什么程度
- **引用密度**：每 1000 字大约引用几篇文献
- **语言风格**：偏学术化还是偏工程化，术语使用习惯

如果范文是 PDF，提示用户转换为 .docx 或直接粘贴文本。

### W1.3 代码分析

如果用户提供了代码文件，分析代码结构：

1. 查看项目目录树：`find About/ -name "*.py" -o -name "*.java" -o -name "*.js" -o -name "*.go" -o -name "*.cpp" | head -30`
2. 读取关键文件（入口文件、核心模块、配置文件）
3. 分析项目架构（MVC、微服务、单体、前后端分离等）
4. 识别关键技术栈和依赖
5. 理解核心算法和业务逻辑
6. 提取可用于论文的关键信息：
   - 系统架构图可参考的模块划分
   - 核心算法的实现思路
   - 关键数据结构和接口设计
   - 测试用例和性能数据（如果有）

**代码分析原则：**
- 只分析 About/ 中提供的代码，不假设任何功能
- 如果代码不足，在相关章节中标注 `[待补充：具体内容]`
- 提取真实的技术细节（类名、方法名、参数），让论文内容更具体

### W1.4 收集用户信息

使用 AskUserQuestion 工具（或终端输出选项）收集以下信息：

**必填信息：**
1. 论文题目 / Thesis title
2. 论文类型 / Thesis type:（本科毕业设计 / 硕士论文 / 课程论文 / 其他）
3. 专业 / Major
4. 学校 / University
5. 目标字数 / Target word count（本科通常 10000-15000 字，硕士 30000-50000 字）

**选填信息：**
6. 学生姓名 / Student name（用于封面）
7. 学号 / Student ID（用于封面）
8. 指导教师 / Advisor（用于封面和致谢）
9. 完成日期 / Completion date
10. 特殊要求 / Special requirements

**学科识别：**
根据专业自动判断学科类型（文科/理工科/医学/经管），用于后续 AIGC 安全写作的阈值调整。

## Step W2：大纲生成（Outline Generation）

### W2.1 确定论文结构

基于模板结构、范文模式、代码分析和论文类型，生成论文大纲。

**本科毕业设计（理工科）典型结构：**

| 章节 | 内容要点 | 建议字数 | 代码相关 |
|------|---------|---------|---------|
| 前言/绪论 | 研究背景、意义、国内外现状、研究内容 | 1500-2000 | 否 |
| 相关技术/文献综述 | 核心技术原理、理论基础 | 2000-3000 | 否 |
| 系统设计/方法设计 | 总体架构、模块设计、算法设计 | 2500-3500 | 是（核心） |
| 系统实现/实验 | 关键代码实现、界面展示 | 2500-3500 | 是（核心） |
| 测试与结果分析 | 测试方案、测试结果、性能分析 | 1500-2500 | 是（部分） |
| 总结与展望 | 工作总结、创新点、不足、未来方向 | 800-1200 | 否 |
| 参考文献 | — | — | 否 |
| 致谢 | — | 300-500 | 否 |

**硕士论文结构：** 在本科基础上增加 "研究方法""实验设计" 等独立章节，每章字数翻倍。

**文科论文结构：** 绪论 → 文献综述 → 理论框架 → 研究方法 → 实证分析 → 结论。

### W2.2 章节编号格式

使用模板中的编号格式：
- 如果模板使用 "1 xxx" → 使用数字编号
- 如果模板使用 "第一章 xxx" → 使用中文编号
- 如果模板使用 "Chapter 1" → 使用英文编号

### W2.3 输出大纲并等待确认

输出完整大纲（Markdown 格式），包含每章的：
- 章节编号和标题
- 内容要点（3-5 个要点）
- 建议字数
- 是否需要代码支撑

**等待用户确认大纲后再进入 Step W3。** 用户可以修改、增加、删除或调整章节顺序。

## Step W3：逐章撰写（Chapter-by-Chapter Writing）

### W3.1 写作原则

**AIGC 安全写作（全程应用）：**

生成每章内容时，必须主动应用以下技法（参考 `references/rewrite_methods.md`）：

1. **句式重构**: 长短句交替，避免模板化句式
2. **破解模板**: 不使用 "首先/其次/最后" 结构
3. **概念具象**: 用具体数据、真实技术细节替代抽象表述
4. **论证补全**: 多维证据 + 对比 + 限定条件
5. **困惑度提升**: 使用非常规但准确的学术表达
6. **风格断裂**: 不同章节间有意识地切换表达风格
7. **添加主语**: 避免无主句

**一致性维护：**
- 维护一个 "全局上下文摘要"（不超过 200 字），记录已写的核心概念、术语定义、关键数据
- 每章开头回顾全局上下文摘要，确保术语和描述一致
- 每章结束后更新全局上下文摘要

**内容真实性原则：**
- 技术描述基于 About/ 中的实际代码和文档
- 实验数据使用代码中的真实数据（如测试输出、性能指标）
- 如果某些信息缺失，用 `[待补充：xxx]` 标注，不编造

### W3.2 各章节写作指南

**前言/绪论：**
- 研究背景：从行业/社会需求切入，逐步聚焦到具体问题
- 国内外研究现状：引用真实文献（从范文中提取，或使用公开可查的文献）
- 研究内容：列出本文的具体工作，与代码模块对应
- 写作技巧：避免"具有重要意义"等空话，用具体需求驱动

**相关技术/文献综述：**
- 介绍核心技术，按逻辑关系组织（从基础到高级，或从宏观到微观）
- 每个技术点：定义 → 原理 → 优势/局限 → 与本文的关系
- 引用真实的技术文档、论文、官方文档
- 写作技巧：加入个人理解和评价，不堆砌百科式介绍

**系统设计（代码核心章节）：**
- 总体架构：基于代码目录结构描述模块关系
- 模块设计：逐一介绍每个模块的职责、输入输出、核心算法
- 数据库设计（如有）：表结构、ER 关系
- 接口设计（如有）：API 端点、请求响应格式
- **关键**: 从代码中提取真实的类名、方法名、参数

**系统实现（代码核心章节）：**
- 关键代码片段展示 + 逐行解读（选择核心算法，非全部代码）
- 界面截图占位符：`[图 X-X 系统主界面]`
- 核心功能的实现流程描述
- **关键**: 展示真实代码片段（从 About/ 代码中提取）

**测试与结果分析：**
- 测试环境：真实的环境配置（从代码的 README 或配置文件中提取）
- 测试方案：功能测试、性能测试的具体用例
- 测试结果：使用代码中的真实测试数据，或标注 `[待补充：实际测试数据]`
- 图表占位符：`[图 X-X 测试结果对比图]`、`[表 X-X 性能数据表]`

**总结与展望：**
- 工作总结：按章节回顾主要工作
- 创新点：2-3 个具体的技术创新或优化点
- 不足与展望：诚实的局限性讨论 + 2-3 个未来改进方向

**参考文献：**
- 仅包含用户提供的文献列表或范文中引用的文献
- 格式遵循模板要求（GB/T 7714 / APA / IEEE）
- 如果用户未提供文献列表，生成占位文献并标注 `[请替换为实际引用的文献]`

**致谢：**
- 如果用户提供了导师姓名，包含对导师的感谢
- 模板化的致谢结构，但避免 AI 化表达

### W3.3 逐章生成流程

对大纲中的每一章：

1. 在上下文中回顾全局上下文摘要
2. 根据章节类型选择对应的写作指南（W3.2）
3. 生成章节内容（目标字数的 90-110%）
4. 主动应用 AIGC 安全写作技法
5. 输出章节内容到终端
6. 更新全局上下文摘要
7. **暂停并等待用户确认**："本章内容是否满意？需要修改什么？确认后继续下一章。"

用户确认后，将确认的章节文本保存到临时文件中，供 Step W4 使用。

## Step W4：格式应用与输出（Format Application & Output）

### W4.1 组装全文

将所有已确认的章节内容组装为一份 Markdown 文件。

格式说明：
- `# 标题` → 一级标题（章标题）
- `## 标题` → 二级标题（节标题）
- `### 标题` → 三级标题（小节标题）
- 正文段落直接书写
- 图表占位符用 `[图 X-X 描述]` 或 `[表 X-X 描述]`

### W4.2 生成格式化 .docx

使用 `docx_io.py formatted_write` 命令生成格式化文档：

```bash
python3 ~/.claude/skills/aigc-detector/scripts/docx_io.py formatted_write "output/<论文题目>.docx" --template "About/<模板文件名>" < assembled_thesis.md
```

`formatted_write` 会自动：
1. 从模板复制页面布局（纸张大小、页边距）
2. 按模板格式设置各级标题和正文的字体、字号、加粗
3. 应用行距、首行缩进等段落格式

### W4.3 输出格式化摘要

告知用户：
- 输出文件路径
- 尚需手动处理的事项：
  - 插入图片（替换 `[图 X-X]` 占位符）
  - 调整封面信息（姓名、学号、日期等）
  - 在 Word 中自动生成目录（引用 → 目录）
  - 检查页眉页脚、页码
  - 检查参考文献格式

## Step W5：AIGC 检测与优化（Detection & Optimization）

### W5.1 执行检测

对生成的完整论文执行现有的检测流程：

1. 使用 `docx_io.py read` 读取刚生成的 .docx 文件
2. Step 0: 语言检测
3. Step 2: 5 维度语义分析
4. Step 3: 输出检测报告

### W5.2 改写优化

如果整体风险评分 > 30%：

1. 按改写优先级逐段改写高风险和中风险段落
2. 应用 `references/rewrite_methods.md` 中的技法
3. 保持学术严谨性，不改变核心内容
4. 使用 `docx_io.py replace` 命令替换高风险段落

### W5.3 迭代检测（可选）

如果第一次改写后风险评分仍 > 30%，询问用户是否继续迭代改写。

### W5.4 输出最终版本

输出最终 .docx 文件和检测报告摘要。

## 图表自动识别与生成规则

### 各章节推荐图表类型

| 章节类型 | 推荐图表 | Mermaid 类型 |
|---------|---------|-------------|
| 需求分析 | 用例图、功能结构图 | `graph TD` |
| 系统设计 | 系统架构图、模块关系图 | `graph TD` 或 `graph LR` |
| 数据库设计 | ER 关系图 | `erDiagram` |
| 详细设计 | 类图、时序图、状态图 | `classDiagram` / `sequenceDiagram` / `stateDiagram-v2` |
| 系统实现 | 功能流程图 | `graph TD` |
| 测试分析 | 测试流程图、结果对比 | `graph TD` |

### 图表生成工作流

写每章内容时，LLM 应按以下步骤处理图表：

1. **识别位置**：分析章节内容，判断哪些位置适合用图表辅助说明
2. **保留占位符**：在正文中保留 `[图 X-X 描述]` 占位符
3. **输出建议**：在章节末尾列出图表建议，包含：
   - 插入位置（段落编号）
   - 图表类型和描述
   - 完整的 Mermaid 代码
4. **用户确认**：询问用户是否生成以上图表，允许修改或跳过
5. **生成并插入**：用户确认后调用 `diagram_gen.py` 和 `docx_io.py insert_figure`

### Mermaid 质量要求

- **节点标签用中文**，类名/方法名保持英文（如代码中有）
- **单图不超过 20 个节点**，过大则拆分为多张子图
- **内容必须与论文上下文一致**，不得编造不存在的模块、类或关系
- **类图需基于实际代码分析**，从 About/ 代码中提取真实的类名、属性和方法
- **ER 图需基于实际数据库设计**，表名和字段名应与代码一致
